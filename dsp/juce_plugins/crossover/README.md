# crossover

A two-way **linear-phase FIR crossover**. Mono input. Output 1 is the low band (woofer),
output 2 the high band (tweeter).

```
in ─┬─ gain ─ FIR lp[] ─► out 1 (low)
    └─ gain ─ FIR hp[] ─► out 2 (high)
```

The taps come from `crossover_coefs.hpp` (`float lp[N]`, `float hp[N]`), compiled in. The
header is generated by the tuning GUI (*Export C++ headers*), which writes it straight into
this folder. It is designed with Parks-McClellan (`scipy.signal.remez`) at the crossover
frequency / transition width / tap count set in the GUI.

To change the crossover, re-export from the tuning GUI and rebuild:

```bash
../tools/build-podman.sh crossover            # then -install to deploy
```

The per-band delays the tuning GUI uses for time alignment are simulation-only. They are
not part of this header, so apply them in the host or in the signal chain.

## Builds

Since 0.0.4 the crossover builds, like `loudness`, as three targets from one source
([../README.md](../README.md#control-and-headless-builds)): `crossover`, the complete plugin, as
before; `crossover_control`, the parameters and the editor with no DSP, which the controller app
compiles in, so it shows the crossover's own editor with its real pins (one input, two outputs)
instead of a placeholder; and `crossover_headless`, the parameters and the DSP with no editor,
for `speakerd` on a speaker (`tools/build.sh crossover aarch64 headless` from the repository
root cross-builds it, into `build/aarch64/crossover/`). The DSP (the two bands and the bypass)
is in `CrossoverDsp.cpp`, which the control build leaves out together with the coefficient
header: its `processBlock` and `processBlockBypassed` leave the audio untouched. The parameter
layout and the state are the same in all three, and the processed output is 0.0.3's bit for
bit, so the bypass test's reference stays. `../../juce_apps/plugin-check/run.sh crossover`
checks all of that with the gain at -12 dB (`plugin-check.probes`).

Each band's FIR is the shared block FIR, `../shared/blockfir/BlockFir.h` (`SHARED blockfir`
in `CMakeLists.txt`, [../README.md](../README.md#shared-source-folders)), after the band's gain.
Since 0.0.2 it replaces `juce::dsp::FIR::Filter`, a patch whose tolerance is, as measured: on
x86_64 the same output bit for bit; on aarch64 every tap is a fused multiply-add, which differs
from `FIR::Filter`'s mix of fused and unfused taps by less than -131 dB re the FIRs' peak
(`../tests/blockfir`, full-scale noise), and the plugin's two outputs differ from 0.0.1's by
-129.5 and -132.6 dB re their peak (rendered by `speakerd` from a sweep and noise). A block
longer than the one prepared is processed in chunks of that size.

| Parameter | Range | Default | |
|---|---|---|---|
| Gain | −30 … 0 dB | 0 dB | applied to both bands; a change ramps over 10 ms (since 0.0.3) |
| Freq | | | unused (left over from the plugin template) |

The gain's default was written `0.5f` up to 0.0.2, a value outside the range, which every host
and the APVTS read as the range's end, 0 dB; 0.0.3 writes 0 dB, so the layout is unchanged.

## Bypass

Since 0.0.3, a bypassed crossover keeps its gain and splits nothing: **output 1** (the woofer's)
is the input times the gain, delayed by the FIRs' (259 − 1) / 2 = 129 samples, and **output 2**
(the tweeter's) is silence, so that a bypassed crossover never gives a tweeter the full range,
whatever routes it there. Both paths run in every block, so a change fades from one to the other
over 10 ms (`../shared/bypass/LevelMatchedBypass.h`) when a host toggles the bypass of a running
instance; `speakerd` applies a bypass by building a new graph for the new revision, whose new
instance starts in its state with no fade (`BypassFade::reset`), under `speakerd`'s own fade
around the swap. It is `processBlockBypassed()`, which every
host calls for a bypass (JUCE's LV2 wrapper when its `lv2:enabled` port is 0, as a node bypass in
`speakerd` sets it); the crossover has no bypass parameter of its own, so no saved state carries
one ([lv2-bypass.md](../../docs/juce-knowledge/hosting/lv2-bypass.md)).

Up to 0.0.2 a bypass was JUCE's default: output 1 the input as it is, output 2 silence. Measured as
for firConv ([its README](../firConv/README.md#bypass), `../tests/bypass`), output 1:

| Signal | Gain | Processed | Bypassed, 0.0.2 | Bypassed, 0.0.3 | Bypassed − processed, 0.0.2 | 0.0.3 |
|---|---|---|---|---|---|---|
| pink noise | −12 dB | −42.78 dBFS | −29.82 dBFS | −41.82 dBFS | +12.96 dB | +0.96 dB |
| pink noise | 0 dB | −30.78 dBFS | −29.82 dBFS | −29.82 dBFS | +0.96 dB | +0.96 dB |
| 1 kHz sine | −12 dB | −35.01 dBFS | −23.01 dBFS | −35.01 dBFS | +12.00 dB | 0.00 dB |
| 1 kHz sine | 0 dB | −23.01 dBFS | −23.01 dBFS | −23.01 dBFS | 0.00 dB | 0.00 dB |

The +0.96 dB on pink noise is the high band that the low band does not carry. Output 2 is silence
when bypassed (processed: −49.0 dBFS of pink noise at −12 dB). At a constant gain the processed
outputs are the same as 0.0.2's bit for bit, both of them: `../tests/bypass` builds 0.0.2 from
its sources in git and compares the two renders sample for sample.

The editor's plot does not read the filters: it draws `getMagnitudes()`, which nothing fills,
so it shows a flat line at the bottom of the plot, in the control build (which has no filters)
as in the complete one.

Latency: a linear-phase FIR delays by (N − 1)/2 samples, e.g. 129 samples (2.7 ms at
48 kHz) for the shipped 259-tap design.
