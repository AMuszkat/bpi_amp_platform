# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this directory is

Out-of-tree kernel customization for a **BananaPi BPI-CM4** module on a **CM4IO baseboard** (Amlogic A311D, `g12b` SoC). The end goal is dual **MAX98397** I2S/TDM smart amplifiers (driven by the in-tree `max98396` codec driver) wired to the SoC's TDM_A interface, exposed to userspace through PipeWire.

This is the `firmware/` half of the BPI AMP Platform repo (the KiCad boards live in `../hardware/`). It holds *only* the deltas — device tree, kernel `defconfig`, patches, locally-iterated drivers, PipeWire config, and the setup scripts that install the remote plugin host on a board (`setup.sh`, `speakerd-setup.sh`, `snapcast-setup.sh`, `ampd-setup.sh`) and `ampd`, the speaker's network agent. It does **not** contain a kernel tree. The mainline source (stable `v6.12.22`) is expected at `linuxMainLine/` (gitignored via `/linux*/`) or wherever `LINUX` points in `local.mk`, referenced as `$(LINUX)` in the Makefile.

## Build & deploy workflow

The top-level `Makefile` cross-builds on the host and pushes artifacts to the live board over SSH. Key variables at the top of `Makefile` must match the board's running kernel: `TARGET_KERNEL1/2`, `DTB1`. The board address, ssh user and kernel tree path are **not** in the repo (it is public): they come from `local.mk` (gitignored; template `local.mk.example`) or the environment — `BOARD_HOST`, `BOARD_USER`, `LINUX`. `TARGET_MACHINE` defaults to `root@$(BOARD_HOST)`. Never commit real hostnames, IPs or usernames; use placeholders like `bpi-amp.local` / `user` in docs and examples.

```sh
make config          # copy defconfig into $(LINUX), run `make defconfig`, scp .config to board
make image           # build Image, gzip -> vmlinuz-$(TARGET_KERNEL)
make dtbs            # copy meson-*.dts/.dtsi into the kernel tree and build DTBs
make modules         # build kernel modules
make patch           # git-apply every patch/*.patch into $(LINUX)
make all             # image + install_image + dtbs + install_dtbs + modules + install_modules + initrd + update_symlink
make install         # install_image + install_dtbs + install_modules (no rebuild)
```

`install_*` targets `scp`/`ssh` directly into the target's `/boot` and `/lib/modules`. `make all` reboots-worthy: it also regenerates initrd and flips the `/boot` symlinks. There is no test suite — verification is done by booting the board and checking ALSA/PipeWire.

Note `make dtbs` **overwrites** `$(LINUX)/arch/arm64/boot/dts/amlogic/Makefile` to build only `DTB1`.

## Local on-target module iteration (`localBuild/`)

`localBuild/` exists to rebuild individual codec/sound-card modules **natively on the board** (against `/lib/modules/$(uname -r)/build`) rather than cross-compiling the whole tree — much faster for driver iteration. `localBuild/Makefile` ssh's source to the board, builds, and copies the `.ko` back here *and* into the board's module tree.

```sh
cd localBuild
make all          # build & deploy dummy-codec-am.ko
make axg_card     # build & deploy snd-soc-meson-axg-sound-card.ko
make max98396     # build & deploy snd-soc-max98396.ko  (source: max98396.c/.h)
```

`targetMakefile_*` are the per-module kbuild Makefiles shipped to the board (renamed to `Makefile` on the far side). Update `TARGET_KERNEL` in `localBuild/Makefile` when the board's kernel changes.

## Audio architecture (the core of this project)

Signal path out: `FRDDR_A` (DMA fifo) → `TDMOUT_A` → `TDM_A` interface → two MAX98397 amps on I2C2, sharing one 8-slot TDM bus. Signal path back: the amps' `DOUT` telemetry → `TDM_A` → `TDMIN_A` → `TODDR_A`, added for the amplifier scope (see **Amplifier telemetry** below).

- **`meson-g12b-bananapi-cm4-cm4io.dts`** — baseboard DT. Defines the `amlogic,axg-sound-card` `sound` node and its `dai-link`s. The two amps are declared under `&i2c2` as `max98397_1` (`reg=0x39`, `amp1`) and `max98397_2` (`reg=0x38`, `amp2`), both `compatible = "adi,max98397"`. `dai-link-2` uses `dsp_a` format, 8 slots, 32-bit slot width (it was `dai-link-1` until the `toddr_a` capture front end took that index).
- **`meson-g12b-bananapi-cm4.dtsi`** — module-level DT (regulators, eMMC/SDIO, CPU OPP, `&tdmif_a`/`&tdmout_a`/`&frddr_a` enablement, pinctrl). Edit here for anything module-wide; edit the `.dts` for baseboard/audio-card topology.
- **`localBuild/max98396.c` / `.h`** — local copy of the in-tree MAX98396 codec driver (the MAX98397 is handled by this driver). This is where amp-driver fixes are prototyped before upstreaming.
- **`localBuild/snd-soc-meson-axg-sound-card.c`** — local copy of the Amlogic AXG sound-card machine driver, for iterating on DAI-link / multi-codec handling.
- **`localBuild/dummy-codec-am.c`** — a minimal stub ASoC codec (`custom,dummy-codec-am`, DAI `dummy-codec-am-hifi`) used to bring up / debug the TDM link without real amp hardware. Its DT node is currently commented out in the `.dts`.
- **`pipewire/pipewire.conf`** — PipeWire daemon config (v0.3.65). Pinned to `default.clock.rate = 44100` and `link.max-buffers = 16`. Deploy to `/etc/pipewire` or `~/.config/pipewire` on the board (`setup.sh --base-conf` does, keeping the board's own as `.orig`). Its amplifier object has `priority.driver = 1000`, so the DAC drives every graph it is in (see "speakerd on a board"). **Name mismatch:** this file calls the amplifier `alsa-playback-pcm`, while `snapcast-setup.sh`'s client-rt.conf and speakerd's default use `bpi-alsa-playback-pcm`, so the running boards' own config presumably differs from this one; the speakerd installer detects whichever exists.
- **`pipewire/pipewire.conf.d/60-speakerd-sink.conf`** — the persistent `speakerd` sink, a drop-in the speakerd installer puts in `~/.config/pipewire/pipewire.conf.d/` (see "speakerd on a board").

When changing the TDM topology, the DT (`dai-link` slots/masks), the codec DT nodes, and the amp driver's slot configuration must stay consistent, or the card won't probe.

## Amplifier telemetry (measurement ADC + IV sense)

The MAX98397 can report what it is doing to itself, by two routes, and both needed driver work
before anything came out. This is what the `ampScope` JUCE plugin (a separate
project) reads.

Both routes are things the **driver** publishes -- the ALSA control interface and an ALSA capture
stream. Userspace never touches the part directly (`max98397-diag.py` is the deliberate exception,
and it exists to read latched fault bits the driver does not expose). Anything a client needs that
is not on one of those two interfaces is a gap in the driver, which is how the slot-report controls
below came to exist.

**Route 1 -- the measurement ADC, through the control interface.** A 9-bit ADC with PVDD, VBAT,
VDDH_SNS and thermal channels, read back through the driver's `ampN ADC PVDD` / `ADC VBAT` /
`ADC VDDH` / `ADC TEMP` mixer controls, which the driver services over I2C. Those controls existed already but **always read zero**: nothing ever enabled the
channels. They are manual enables in *Meas ADC Config*, which on the '97 is **0x20C8**, not the
'96's 0x20C7 -- 0x20C7 on a '97 is *Meas ADC Optimal Mode*. `max98396_telemetry_setup()` now
switches PVDD, VBAT and (on a '97) VDDH on at probe. This touches no pin, so it is unconditional.
Conversions, from the Rev 3 datasheet: PVDD and VDDH are 54.703125 mV per code, VBAT 11.3965 mV,
thermal 1 degC per code minus 252 degC.

**Route 2 -- voltage/current sense on DOUT, through a capture stream.** IV sense is a continuous
16-bit-per-sample stream at 48-192 kHz, so a PCM device is the right interface for it and the
control interface could not carry it however much the driver were extended. This is the one that
behaves like a scope, and it needed four separate fixes plus a device-tree capture path.

The '97's register map is the '96's with **two extra TX Control registers inserted**, so everything
from the Hi-Z block onwards shifts. The local driver had already been fixed for RX Source and Bypass
Source (0x2055/0x2056/0x2058 -> 0x2057/0x2058/0x2059); the transmit side had not:

| what | '96 | '97 | what the driver had |
|---|---|---|---|
| PCM TX Control 9 / 10 (THERM, ICC slots) | -- | 0x204C / 0x204D | 9 only |
| PCM Tx HiZ Control 1..8 | 0x204C..0x2053 | **0x204E..0x2055** | 0x204D..0x2054 (off by one) |
| PCM TX Source Enables | 0x205D | **0x205C** | wrote 0x205D on both |
| PCM TX Source Enables 2 (THERM) | -- | 0x205D | -- |
| PCM Tx Supply Select | -- | 0x2060 | present |
| Meas ADC Optimal Mode | -- | **0x20C7** | called 0x20C5 |
| Meas ADC Config (channel enables) | 0x20C7 | **0x20C8** | never written |

Consequences of the old addresses, all of which had to be true at once for the feature to be dead:
writing VMON|IMON to 0x205D on a '97 set the *thermal* enable and left voltage and current sense
off; and the Hi-Z block being one register low meant slots 0-7 kept their reset value of 0xFF, so
those slots were Hi-Z no matter what. Nothing was ever driven on DOUT.

Also fixed: transmit slot numbers are **6 bits on the '97** (64 slots), not 4 -- the driver masked
every `adi,*-slot-no` with 0xF, which cannot reach past slot 15, and an 8-channel 32-bit frame is 32
amp slots wide. And the codec DAI's `capture.channels_max` was 2, which is not enough once a supply
rail and the temperature have slots of their own; it is now 8.

**Slots are 8 bits.** A transmit frame is up to 64 sequential 8-bit slots, so one 32-bit TDM slot
covers four of them and a 16-bit datum at amp slot *s* lands in TDM channel *s*/4, shifted left by
`16 - 8 * (s % 4)`. `s % 4 == 3` straddles two channels. This is the single most confusing thing
about the part and is why the board's slot plan counts in fours. The slot registers confirm it:
their decode reads "0x0: Slot 00/01, 0x1: Slot 01/02, ...", i.e. the value names the FIRST of the
two 8-bit slots a 16-bit datum occupies.

**What can go on the bus.** Per Table 6, the '97 can transmit voltage sense, current sense, the DSP
monitor, the applied DHT attenuation, Supply1 (PVDD), Supply2 (VBAT), the BPE level, device status
flags, ICC data and the die temperature -- each with its own enable and slot. So the supply rail is
genuinely available at the PCM sample rate, not only through the I2C readback; the board uses that
for PVDD and leaves Supply2 unassigned (VBAT is a 5 V housekeeping rail and the capture is kept to
four channels).

**New device-tree properties** (all on the codec node, all optional):

- `adi,telemetry-enable` -- the opt-in that actually lets the amp drive its slots. Without it the
  driver leaves DOUT fully Hi-Z exactly as before. It is gated on purpose: the amps share one DOUT
  line and arbitrate only by Hi-Z, so two amps driving the same slot is two push-pull outputs
  shorted together.
- `adi,supply1-slot-no`, `adi,supply2-slot-no`, `adi,therm-slot-no` -- '97 only; unset means that
  data type is not transmitted at all. **Supply1 and Supply2 are named, not generic**: the transmit
  enables define them, `PCM_SUPPLY1_EN` = "enables transmit of the measured PVDD supply voltage",
  `PCM_SUPPLY2_EN` = "the measured VBAT supply voltage". So `supply1-slot-no` puts PVDD on the bus
  and `supply2-slot-no` puts VBAT on it, and a capture client can decode them without being told.
- `adi,supply-select` -- the raw `SUPPLY_SELECT[1:0]` value, default 0. **Not an enum, because the
  datasheet does not document one**: the DECODE column for that field (0x2060) is a copy-paste of
  `PCM_TX_EN`'s ("0: PCM data output disabled / 1: enabled"), which cannot be what a 2-bit supply
  selector means. The reset state is the documented one -- Supply1 = PVDD, Supply2 = VBAT -- so
  leave it at 0 unless you have better information than the datasheet gives. An earlier version of
  this driver exposed it as an enum reading "PVDD / VBAT / VDDH"; that mapping was invented.

**New ALSA controls.** Enables and rates for the measurement ADC (`Meas ADC PVDD Switch`,
`… VBAT Switch`, `… VDDH Switch`, `… PVDD Rate`, `… VBAT Rate`, `… VDDH Rate`,
`… PVDD Filter Switch`, `… PVDD Filter BW`); the DOUT source enables (`PCM VMON Switch`,
`PCM IMON Switch`, `PCM Supply1 Switch`, `PCM Supply2 Switch`, `PCM Therm Switch`) and the raw
`PCM Supply Select`; the '97's `ADC VDDH`, `ADC Lowest PVDD` and `ADC Lowest VDDH` readbacks; and
five **read/write** slot controls, `PCM VMON Slot` / `PCM IMON Slot` / `PCM Supply1 Slot` /
`PCM Supply2 Slot` / `PCM Therm Slot`, where 64 means "not transmitted". Writing one gives the old
slot back to the bus before claiming the new one (so a move never has this amp driving two slots at
once) and switches that data type's transmit enable to match -- a data type with nowhere to go and
one that is switched off are the same thing, so probe and the controls derive the enables the same
way. This is what lets a client lay the frame out at runtime instead of only through the DT.

**The one control nothing works without** is `ampN VI Sense Switch`. It is a DAPM switch in front of
`PCM_TX_EN`, so the whole transmit path stays powered down until userspace closes it -- the amp is
silent however its slots are set. `ampScope` writes it (with the two `Meas ADC * Switch` rails behind
the supply data types) at start-up and on every device change. Those four exist so a capture client can find this amp's data in the frame without
being told -- with several amps on one DOUT line the answer differs per amp, and nothing else in
userspace knows it.

**Device tree: the capture path.** `meson-g12b-bananapi-cm4.dtsi` adds `&tdm_a_din0_pins` to
`&tdmif_a` and enables `&tdmin_a` and `&toddr_a`; `meson-g12b-bananapi-cm4-cm4io.dts` adds
`&tdmin_a` to `audio-aux-devs`, the routes `"TDMIN_A IN 0", "TDM_A Capture"` and
`"TODDR_A IN 0", "TDMIN_A OUT"`, a `toddr_a` front end (which renumbered the TDM link to
`dai-link-2`), and `dai-tdm-slot-rx-mask-0 = <1 1 1 1 0 0 0 0>`. The slot plan:

```
amp slot  0 /  2  -> TDM slot 0: amp1 VMON | amp1 IMON
amp slot  4 /  6  -> TDM slot 1: amp2 VMON | amp2 IMON
amp slot  8 / 10  -> TDM slot 2: amp1 PVDD | amp1 TEMP
amp slot 12 / 14  -> TDM slot 3: amp2 PVDD | amp2 TEMP
```

**Untested against hardware.** The driver builds clean (W=1) and the DTB compiles, but whether the
CM4IO baseboard actually routes the amps' DOUT to the SoC's TDM_A DIN pin is a wiring question this
repo cannot answer. If it does not, route 2 will stay silent and only the I2C measurement ADC works;
that is exactly what ampScope's "Control (I2C)" source is for.

## MAX98397 fault diagnostics (`max98397-diag.py`)

`max98397-diag.py` runs **on the board** and reads (or clears) the MAX98397's latched interrupt/fault registers directly over I2C, to chase clicks/pops during playback. It's dependency-free Python — it talks to the bus via the Linux `i2c-dev` `I2C_RDWR` ioctl (16-bit register addressing), so it needs **no i2c-tools** and works even while the `max98396` driver has the device bound (the `I2C_RDWR` path skips the `I2C_SLAVE` busy check, like i2ctransfer's `-f`). Needs **root** (`/dev/i2c-2` is `root:i2c`; the default board user isn't in the `i2c` group). Auto-detects bus+addrs from `/sys/bus/i2c/drivers/max98396/<bus>-00<addr>` (→ bus 2, 0x38 amp2 / 0x39 amp1).

- Reads **INT_STATE** (0x2006–0x2009, latched + *unmaskable* — the primary "accumulated errors", catches events even if the driver didn't enable that IRQ) and **INT_FLAG** (0x200B–0x200E, driver-enabled IRQ sources); `--raw` adds **INT_RAW** (0x2001–0x2004, live). `--clear` writes 0xFF to **INT_FLAG_CLR** (0x2015–0x2018). Connectivity sanity via **REV_ID 0x22FF** (the '97's; the '96 uses 0x21FF), plus GLOBAL_EN (0x210F) and BPE_STATE (0x20E5).
- Decodes each bit with severity and flags the click/pop suspects (`*`): clock/data monitor (`CLK_ERR`/`DMON_ERR`/`INT_CLK_ERR`/`INT_SPKMON_ERR`/`CLK_RECOVER` → I2S/TDM glitch/underrun → amp mutes → click), supply (`PVDD_UVLO_SHDN`/`*_UVLO`/`BPE_*` → brownout → pop), `SPK_OVC`, thermal (`THERM*`/foldback). Prints an interpretation summary tying clock errors back to PipeWire xruns/quantum.
- `--watch [sec]` clears then polls (default 0.5s), printing faults as they fire and a per-bit count summary on Ctrl-C — run it while playing the sine sweep to correlate audible clicks with which register bit latches.
- Device select: `--addr 0x38` (amp2) / `--addr 0x39` (amp1), repeatable, default both. Arbitrary register access: `--reg 0xADDR` reads one 16-bit register (auto-decoded if it's a known interrupt reg), and `--reg 0xADDR --set 0xVAL` pokes it (warns — can fight the driver's regmap).

Workflow: `sudo ./max98397-diag.py --clear` → play the sine/sweep → `sudo ./max98397-diag.py` (or `sudo ./max98397-diag.py --watch 0.25` live). Register/bit map source: `localBuild/max98396.h` + the MAX98397 datasheet (Analog Devices).

## Synchronized network audio streaming (`snapcast-setup.sh`)

`snapcast-setup.sh` sets up **Snapcast over PipeWire** to stream audio from a Linux host (server) to one or more Linux boards (clients), with tight (~1 ms) inter-client sync — suitable for a synchronized stereo pair (two boards as L and R). Snapcast was chosen over Roc Toolkit because Roc's per-receiver latency loops drift (no inter-receiver sync), whereas Snapcast schedules playback against a shared server clock. The trade-off is a buffered end-to-end latency (`--buffer`, default 1000 ms; lower for less delay, higher for Wi-Fi robustness).

Architecture:
- **Server (host):** the host is always assumed to run PipeWire, so `snapserver` uses Snapcast's **native `pipewire://` source** (confirmed built into the Ubuntu 0.34.0 package) — `source = pipewire://?name=multi-room&capture_sink=true` (do **not** add `send_silence=true` — with the pipewire capture source it feeds clients silence instead of the captured audio, so the receiver plays nothing). With `capture_sink=true` the source creates **its own single capture sink** (shown as "Snapcast/multi-room" in pavucontrol/qpwgraph) — route audio there to stream it. Do **not** add a separate `null-audio-sink`: snapserver always makes its own, so a hand-rolled one is just an unlinked decoy (an earlier version of this script did that and produced two confusing "Snapcast" nodes, the pretty-named one being dead). Note snapserver's sink has no `node.description`, so `wpctl`/pavucontrol may label it `(null)` even though qpwgraph shows `Snapcast/multi-room`; WirePlumber `stream.rules` can't rename it (it's an `Audio/Sink`, not a `Stream/*`). Because the native source needs the user's PipeWire session, snapserver runs as a **systemd user service** (`~/.config/systemd/user/snapserver.service`); the packaged *system* service is disabled to avoid a port clash, and `loginctl enable-linger` keeps it headless. Managed `/etc/snapserver.conf` backs up any original to `.orig`. Re-running `--mode host` also deletes a stale `60-snapcast-sink.conf` from the old decoy approach. The host setup also writes a **PipeWire quantum/rate drop-in** at `~/.config/pipewire/pipewire.conf.d/10-quantum.conf` (min/max-quantum 64/1024, `default.clock.rate = 48000`, with commented knobs for `force-quantum`/`allowed-rates`) — bigger quantum buys headroom against xruns/clicks in the captured stream — then restarts the user PipeWire (`pipewire`/`pipewire-pulse`/`wireplumber`) so it applies before snapserver starts. Skip with `--no-quantum`. The drop-in rate (**48000**) is aligned with the default `--sampleformat 48000:32:2` so PipeWire does not resample; if you change the stream rate, change both.
- **Client (board):** `snapclient` uses its **native PipeWire player** (`--player pipewire`), so it appears as a node ("Snapcast") in the board's PipeWire graph; routing that node to the AXG/MAX98397 sink is left to the user / WirePlumber (no auto channel-split — see history note below). It runs as a **systemd user service** (`~<user>/.config/systemd/user/snapclient.service`; user from `--client-user`, else the `user@` of `--target-host`, else the invoking/sudo user, else `$BOARD_USER`) sharing that user's PipeWire; the packaged system service is disabled and `loginctl enable-linger` keeps it headless. **Version gotcha:** the board's stock snapclient may be too old for `--player pipewire` (e.g. Debian bullseye ships 0.26.0, which has no pipewire player and exits with "No audio player support for: pipewire"). `ensure_snapclient_with_pipewire` checks for the player (`strings … | grep pipewire_player`) and, if missing, downloads the matching official release `.deb` — specifically the **`_with-pipewire`** variant for the board's `dpkg --print-architecture` + `/etc/os-release` `VERSION_CODENAME` (e.g. `snapclient_0.34.0-1_arm64_bullseye_with-pipewire.deb`) — and `apt-get install`s it (deps auto-resolved). Default version `--snapclient-version 0.34.0` to match the server.
- **Routing into speakerd (`--route speakerd|plugin-host`, default `plugin-host`):** `--route speakerd` writes a client-rt.conf that sends snapclient, shairport-sync and an AudioPluginHost's playback into the `speakerd` sink (speakerd plays it to the amplifier); `--route plugin-host` is the AudioPluginHost route below, unchanged. `--route speakerd` is **refused** unless a PipeWire config of the user (`~/.config/pipewire/pipewire.conf[.d]`, `/etc/pipewire/...`) defines a node `speakerd` **and the running PipeWire has that node with the drop-in's properties** (`priority.session` 1500, `priority.driver` 0, read with `pw-dump`): a target that does not exist sends snapclient to the default sink, the amplifier, full range, and a sink speakerd made itself is gone at the next PipeWire restart. The first route into speakerd keeps the client-rt.conf there was as `client-rt.conf.before-speakerd`, which the speakerd uninstall puts back. `--routing-only` rewrites only client-rt.conf and restarts snapclient (no install, no `--server-ip`); `setup.sh` and the speakerd uninstall use it. The rules reach snapclient only through its unit's `Environment=PIPEWIRE_CONFIG_NAME=client-rt.conf`, so `--routing-only --route speakerd` is **refused** when the snapclient unit lacks that line (re-run `--mode target --server-ip …`, which rewrites the unit, or add it), and `--route speakerd` with `--no-client-rt` is refused; into `Ap.cap` it only warns, as before. Every file it writes in the user's home (client-rt.conf, the unit) is written whole: a temporary file beside it, then a rename. `--client-home <dir>` is a test hook (writes into `<dir>`, no root, no services; the live check is skipped only when no PipeWire is reachable).
- **Client auto-routing (`client-rt.conf`):** the target setup also deploys `~/.config/pipewire/client-rt.conf` (from `target_client_rt_conf()`; backs up any existing to `.orig`) whose `stream.rules` auto-connect nodes as they appear — snapclient → **`Ap.cap`**, AudioPluginHost output → the amp sink (`bpi-alsa-playback-pcm`), AudioPluginHost input ← AirPlay (`Ap.play`), shairport → AirPlay capture (`Ap.cap`). **Persistent-target rule (the important one):** snapclient must target a node that exists *from boot*. `Ap.cap`/`Ap.play` are created by a `module-loopback` in `pipewire.conf`, so they're always present (like the amp) — targeting them links at boot with no race. The AudioPluginHost's own input (`ALSA Capture`) is **transient** (exists only while that GUI app is open, which happens *after* snapclient starts), so pointing snapclient there makes WirePlumber fall back to the default sink (the amp) at boot — the reported bug. Targeting `Ap.cap` (the same loopback shairport feeds) reaches the plugin host via `Ap.cap → Ap.play → AudioPluginHost input`, exactly like AirPlay. (WirePlumber 0.4.13 — bookworm — has no `node.linger`/`node.dont-fallback`, and `node.dont-reconnect` *destroys* the persistent snapclient node instead of waiting, so the persistent-target approach is the only clean config-only fix; `node.linger` would work on WP 0.5+.) **Config gotcha:** snapclient (native pipewire player) loads `client.conf`, *not* `client-rt.conf`, so the unit sets `Environment=PIPEWIRE_CONFIG_NAME=client-rt.conf` to point it at that file (same reason a `client-rt.conf.d` drop-in for `resample.quality` had no effect but `client.conf.d` did). Skip with `--no-client-rt` (snapclient then uses the default `client.conf` and the node must be wired manually). Adjust the `target.object` values in `target_client_rt_conf()` to match your own graph's node names.

Modes mirror the build workflow: `--mode host` (server here), `--mode target` (client here, needs `--server-ip`), `--mode target-remote` (`scp`+`ssh -t … sudo` to `--target-host`, default `root@$BOARD_HOST` (placeholder `bpi-amp.local`), server IP auto-detected, `--client-user` and the ssh user from `user@host` forwarded), `--mode both` (server here + remote client). Server ports: 1704 stream / 1705 control / 1780 http. `--dry-run` prints all config without applying.

History note: an earlier version did automatic L/R channel-split on the client via a `null-audio-sink` + `module-loopback` (`stream.dont-remix`), driven by `--channel left|right`. That was removed in favor of the user wiring the node manually; if a synchronized stereo pair is wanted again, that split approach is the reference.

## speakerd on a board (`speakerd-setup.sh`)

`speakerd-setup.sh` installs **speakerd**, the headless plugin host of `docs/remote-plugin-host.md` (`dsp/juce_apps/speakerd`, read its README), as a **systemd user service of the audio user** (the one whose PipeWire drives the amplifier, with linger), in place of the AudioPluginHost that does the DSP today. Everything lives in that user's home and runs as that user; run as root it re-executes itself as `--user`/`$SUDO_USER`. It never builds anything.

| Path (in the audio user's home) | What |
|---|---|
| `~/.local/lib/speakerd/<id>/` | one **version**: `bin/speakerd`, `bin/speakerd-run` (the unit's ExecStart), `bin/ampd` (the network agent, "ampd on a board"), `lv2/<target>.lv2`, `VERSION` (git commit, dirty or not, when bundled, architecture, contents; speakerd's version and its whole `--version` line), `setup/` (this installer, so `status`/`rollback`/`uninstall` work on the board without a bundle; its scripts are made executable, since the steps below call them directly). `<id>` is `<commit12>[-dirty]-<hash of bin/ and lv2/>`: the same bundle installs once |
| `~/.local/lib/speakerd/current`, `previous` | symlinks to versions, switched atomically (rename); `installed.log` keeps the order; `--keep N` versions (default 3) |
| `~/.local/lib/speakerd/home/` | speakerd's **HOME**, empty. JUCE's LV2 host reads `~/.lv2` before anything and lilv keeps the first bundle of a URI, so an old copy there (`build-podman.sh -install` puts complete builds in `~/.lv2`) would shadow the bundles named with `--lv2-bundle`. speakerd writes nothing into it and needs HOME for nothing else (proven on the virtual pair) |
| `~/.local/state/speakerd/` | `device.json` and `factory.json`; `graph.json` and `graph.lkg.json` are ampd's and never touched; `ampd.json` is `ampd-setup.sh`'s (see "ampd on a board") |
| `~/.config/systemd/user/speakerd.service` | `firmware/speakerd/speakerd.service`, byte for byte |
| `~/.config/pipewire/pipewire.conf.d/60-speakerd-sink.conf` | `firmware/pipewire/pipewire.conf.d/60-speakerd-sink.conf`: the persistent sink |

- **The bundle.** `speakerd-setup.sh bundle --out DIR [--arch aarch64|native] [--plugin loudness:headless ...]` assembles `bin/speakerd`, `lv2/`, `VERSION` and `firmware/` (the installers) from `build/aarch64/...` (what `tools/build.sh <app|plugin> aarch64 [kind]` makes) or the native `build/`; a missing artifact fails with the `tools/build.sh` command that makes it. Default plugins `loudness:headless crossover:complete firConv:complete` (only loudness has a headless build). Install checks that `bin/speakerd` is an ELF for this machine (`uname -m`), that the contents match the id, with `ldd` that every library speakerd and the plugins need is there (libpipewire-0.3, libstdc++ GLIBCXX_3.4.30, glibc 2.34; libfreetype, libfontconfig; libasound for ampScope), and with `speakerd --version` that it is at least **`SPEAKERD_MIN_VERSION`** (one constant in the script: 0.2.0, which prints `speakerd 0.2.0`), the first speakerd that enforces `device.json`'s limits and fails closed without them. An older one, or one that cannot say its version, would ignore the cap, so install refuses it and so does rollback; the version is recorded in the installed `VERSION` (`speakerd_version=`), with the whole line speakerd printed (`speakerd_build=`; from 0.2.1 `speakerd 0.2.1 (<commit12>[-dirty])`, the commit it was built from), which `status` shows, so two builds of one version can be told apart. When that commit is not the one the bundle was made at, install warns: the artifacts were built before the deployed commit was checked out (build after checking it out). A speakerd that cannot be executed at all (exit 126: a bundle in a `/tmp` mounted noexec) is named as such, not as too old: keep bundles in the home. A plugin with one of the bundle's URIs in a **system LV2 folder** (`/usr/lib/lv2`, `/usr/local/lib/lv2`, which JUCE reads before any `--lv2-bundle`) is named loudly: speakerd would refuse to start (status 2) and the speaker stay silent.
- **The unit** (`speakerd.service`): `After=pipewire.service wireplumber.service`, `Wants=pipewire.service`, no network unit; `Restart=on-failure`, `RestartSec=1`, `RestartPreventExitStatus=2 203` (bad command line or bundle; no program), `RestartForceExitStatus=SIGPIPE` (systemd counts SIGPIPE as clean), `StartLimitIntervalSec=0` (systemd's start limit would leave the speaker silent for good after a burst of failures). Environment: `HOME` the empty folder, `UnsetEnvironment=XDG_CONFIG_HOME`, and `PIPEWIRE_CONFIG_NAME=client-rt.conf`: PipeWire's own `client-rt.conf` (never snapcast's routing file in `~/.config`, which the empty HOME hides) is `client.conf` plus `module-rt`, which gives speakerd's graph thread real-time priority through RTKit or `RLIMIT_RTPRIO`. speakerd 0.2.0 asks for `client-rt.conf` itself too. **Keep speakerd's HOME empty for this as well:** a user's own `~/.config/pipewire/client-rt.conf` (snapcast-setup.sh writes one, a full config without `module-rt`) replaces PipeWire's, so a speakerd started with the real HOME gets no real-time thread.
- **The wrapper** (`speakerd-run`, ExecStart and `ExecStopPost=… --record-exit`): speakerd writes no file and keeps no count of its crashes, so the wrapper keeps a history in `$XDG_RUNTIME_DIR/speakerd/history` (tmpfs: forgotten at reboot) — `start <epoch> <layer>` and `exit <epoch> <class> <detail>` from systemd's `$EXIT_CODE`/`$EXIT_STATUS`/`$SERVICE_RESULT`. Classes: exit 0 or death by TERM/INT/HUP **clean**; exit 2 **badcmd**; exit 3 **pipewire**; any other code, any other signal (SEGV, ABRT, KILL, PIPE…), a core dump or an OOM kill **crash**; a stop that timed out is not a crash. The next `--from`: after a crash `last-known-good`, `factory` once three crashes fell within 60 s, `passthrough` once three starts on factory crashed within 60 s, never a layer above the one that crashed; after exit 3 the same layer; otherwise `current`. A start with no exit recorded counts as a crash. When the last start failed and five did within 60 s, it waits `$SPEAKERD_BACKOFF` (5 s) first, so a speaker that cannot play does not spin. It never starts speakerd while an AudioPluginHost runs: it says so once and waits for it to exit. `speakerd-run --status` reads the history.
- **The persistent sink.** The drop-in makes the `speakerd` sink (`support.null-audio-sink`, `Audio/Sink`, `[ FL FR ]`, `monitor.channel-volumes = false`) exist from PipeWire's start, so a player always has somewhere safe to go, before speakerd and between its restarts; speakerd adopts it. **A null sink is always a driver** (`node.driver = false` is ignored), and PipeWire gives a group of linked nodes to the driver with the highest `priority.driver`. So the sink has `priority.driver = 0`, the lowest there is: **not negative** — PipeWire 0.3.65 compares it as if unsigned, and a sink at -1 drives an amplifier at 1 (measured with `pw-profiler`). An amplifier at 0 ties and drives only because it was created first (the main config's objects come before the drop-in's): the installer warns, and `pipewire/pipewire.conf` gives it 1000. Its `priority.session = 1500` makes it WirePlumber's default sink, so a stream with no target plays through speakerd, not straight into the amplifier (unless a person chose another default with `wpctl`). PipeWire 0.3.65's `pw-dump` does not say who drives and its `pw-top` has no batch mode: `pw-profiler` does (`logging driver <id>`), which needs `libpipewire-module-profiler` (the board's config loads it). **A file is not a sink:** a PipeWire started with another config name (`-c`) or `PIPEWIRE_CONFIG_DIR` does not load `~/.config/pipewire/pipewire.conf.d` at all. Then the only `speakerd` sink is the one speakerd makes itself (priority.driver 0, no priority.session; speakerd says `*** NO INPUT SINK CONFIGURED ...`), which is gone at the next PipeWire restart, so after a reboot snapclient and speakerd would race. So `install`, `sink`, `snapcast-setup.sh --route speakerd` and `smoke` all read the **running** PipeWire's `speakerd` node (`pw-dump`) and refuse (smoke fails) unless it has the drop-in's `priority.session` 1500 and `priority.driver` 0; a PipeWire restart that fails is fatal.
- **device.json** holds only what speakerd knows: `version`, `role`, `amplifier {node, woofer, tweeter}` and `limits {gain_db, tweeter}`. speakerd rejects a file with any other key, a key twice, or the woofer and tweeter on one port, and then plays its **fail-safe defaults**: role mono, amplifier `bpi-alsa-playback-pcm`, -20 dB, tweeter muted; a file **without `limits`** plays the fail-safe limits too (it fails closed), so "no limit" must be written: `"limits": { "gain_db": 0, "tweeter": "on" }`. The installer writes only those keys, refuses an existing file with others or with a duplicate (a person fixes it; a file that is not JSON is replaced with `--role`, kept as `device.json.broken`), and after every (re)start under systemd (install, `limits`, `rollback`) reads speakerd's lines from the journal and fails loudly on `device.json: FAILED`, on `*** NO INPUT SINK CONFIGURED`, on a limits line that is not exactly `speakerd: device: limits: output at <g> dB, tweeter <muted|on>` (with the fail-safe speakerd adds ` (no limits in device.json: the fail-safe)` or ` (device.json not read: the fail-safe)`), on no limits line within 15 s (`SPEAKERD_START_WAIT`; also what a journal the user cannot read looks like), and on a speakerd that is no longer running 2 s later (a bundle shadowed by a system LV2 folder exits 2). It judges only what follows the first `speakerd-run: starting speakerd` line since the restart: a restart of a running speakerd first logs the old instance's `speakerd-run: speakerd ended` (its ExecStopPost), which is not the new one's failure; no start line at all within the wait fails too, as does a `speakerd ended` after the start. **The fail-safe relies on a convention: amplifier port `playback_FL` is the woofer** (and `playback_FR` the tweeter, muted) unless device.json says otherwise; a person confirms it at the board.
- **The amplifier** goes into `device.json` from `pw-dump`: the one ALSA `Audio/Sink`, or among several `bpi-alsa-playback-pcm`, then `alsa-playback-pcm` (the name mismatch above); none or an ambiguous set is refused with the list, and `--amplifier` names it. Its ports are checked: woofer `playback_FL`, tweeter `playback_FR` by default (`--woofer-port`, `--tweeter-port`), printed loudly, because **which port drives which speaker is the board's wiring**, which no script can know. A reinstall keeps `device.json`'s role, amplifier and ports: `--role`, `--amplifier`, `--woofer-port` and `--tweeter-port` each change only themselves (a node or port not given is device.json's, else detected or the default); `--role left|right|mono` is required on the first install.
- **Safety defaults.** Every install writes `"limits": { "gain_db": -20.0, "tweeter": "muted" }` into `device.json` — also a reinstall over limits a person lifted (the rule: every deploy caps until the smoke test). Only `speakerd-setup.sh limits --gain-db G --tweeter-limit on --person-present` lifts the cap (no limit at all: `--gain-db 0 --tweeter-limit on`), after a smoke test with a person at the speaker; `limits --cap` restores it. With limits -20 dB no sample of either output exceeds -20 dBFS, whatever the input or the graph (speakerd clamps at ±10^(gain_db/20)). speakerd applies the limits after the graph (also in passthrough: -20 there gives -40) and fixes them at start, so `limits` restarts it; a broken device.json falls back to speakerd's defaults (mono, `bpi-alsa-playback-pcm`, capped), which smoke treats as a failure. A factory graph that breaks **the tweeter rule** (only a crossover's high band may reach the tweeter: "The tweeter rule" below, defined once in `speakerd/tweeter_rule.py`) is refused. The same check covers a `factory.json` that a later install keeps, and **`limits` turning the tweeter on checks every layer speakerd may load** (`graph.json` and `graph.lkg.json`, ampd's, then `factory.json`) and refuses if any breaks the rule; install warns about such a layer, and `status` marks it with `***`. `--allow-tweeter-without-crossover` accepts such a graph only with `--home` (the virtual pair tests): it is refused on a board and in target-remote mode. Two plugin hosts must never feed the amplifier: install **refuses while an AudioPluginHost runs** (any user; zombies ignored) unless `--stop-plugin-host` (TERM, then KILL; also disables a user or system systemd unit that starts it, recorded in `~/.local/state/speakerd/plugin-host-units` for uninstall; a disable that fails stops the install), and **refuses while anything else would start one again at boot or login**, naming each with what to do: an XDG or LXDE autostart (delete the file), a shell profile, the boot script in `/etc` or a unit for every user (remove the line, or `sudo systemctl --global disable`), the crontab (`crontab -e`), a user or system unit without `--stop-plugin-host` (pass it, or disable the unit). A unit an earlier install disabled does not refuse while it stays disabled. Uninstall re-enables only the units it disabled: what a person removed, they put back. **install refuses first and changes last:** the bundle, the plugin host, device.json, the role, the amplifier and its ports, and the factory graph (converted from the bundle into a temporary file) are all checked before anything is stopped or written; the AudioPluginHost is stopped only then, before PipeWire restarts.
- **The factory layer.** `--factory FILE` installs a graph document (atomic write: temporary file, fsync, rename); `--import-filtergraph FILE` converts the board's current AudioPluginHost session with the installed speakerd (`speakerd --import-filtergraph FILE --prefer-headless --device ~/.local/state/speakerd/device.json --lv2-bundle …`, no PipeWire needed; `--device` maps the session's outputs to the woofer and tweeter ports, so device.json is written first) and checks the result the same way; speakerd itself refuses a session that sends the input straight to the tweeter or uses a `_control` build, unless `--allow-unsafe-routing`, which the installer never passes. Without either, an existing `factory.json` is kept, after the same check (refused: replace it with `--factory` or `--import-filtergraph`); with none, speakerd plays passthrough (woofer only, capped), said loudly.
- **Actions:** `install`, `status` (versions, service, history, device.json, layers, the live sink, links, routing, AudioPluginHost), `rollback` (caps `device.json` again, -20 dB and the tweeter muted, as an install does, since the other version's plugins may filter differently; then swaps `current` and `previous` and restarts, with the start check; rollback again goes forward), `uninstall` (first puts snapclient's routing from before speakerd back, `client-rt.conf.before-speakerd`, or without one writes the AudioPluginHost route with `snapcast-setup.sh --routing-only --route plugin-host`; then reads the node that routing names for snapclient in the running PipeWire, and if it is not there — no `Ap.cap` in this PipeWire, say — or cannot be checked, **stops and disables snapclient** and says so, since WirePlumber would send it to the default sink, the amplifier, full range and uncapped; then stops and removes the unit, the drop-in (restarting PipeWire) and the versions, and re-enables the AudioPluginHost units install disabled; `--purge` also removes the state), `smoke`, `sink` (the drop-in, a PipeWire restart if it changed, and the live check), `check` (what install would refuse; changes nothing), `limits`, `stop-plugin-host` (what `--stop-plugin-host` does to a running AudioPluginHost and its units, alone; without that option it only refuses while one runs: setup.sh runs it before PipeWire restarts), `bundle`. Every action takes `--dry-run`; everything is idempotent. `--mode target-remote [--target-host user@host]` (default `$BOARD_USER@$BOARD_HOST` from the environment or `local.mk`) is a thin wrapper: it bundles (the artifacts for `install` and `check`, from `--arch`, default aarch64), copies the one folder with `tar | ssh --` to a `mktemp -d` in the board's `~/.cache` (not `/tmp`, often noexec), runs `bash -c` of `firmware/speakerd-setup.sh <action> <arguments> --bundle .` there, every argument quoted with `printf %q`, as the ssh user, and removes the folder whatever happens. The ssh user is the board's audio user: `root@` is refused (the installers run as the audio user, who cannot read root's folders). Before it copies anything it applies the **deploy gate** itself (`deploy_gate` in `install-lib.sh`, the same as `tools/board.sh`), for `speakerd-setup.sh` and `setup.sh` alike, whoever runs them: refused while `.claude/lab.lock` exists (this checkout's or the main one's), and unless `tests/.status/<HEAD>.json` says `unit: pass` and `vpair: pass`, both run on a clean tree, and the tree is clean now; `BPI_DEPLOY_OVERRIDE=1`, set by a person in their own shell, bypasses the status (never the lock) and is logged in `tests/.status/overrides.log`. A host ending in `.invalid` (the tests' stand-in board, which nothing resolves) is exempt. `--dry-run` copies too and runs the **board-side** dry run, which changes nothing there; so a remote dry run contacts the board, and the deploy gate treats it so. `--factory` files are copied into the bundle's `extra/`, `--import-filtergraph` names a file on the board.
- **smoke** checks without making a sound — run it with a quiet stream playing, since who drives the graph is measured only while it runs (otherwise it says "NOT measured") — reports every check and always prints its summary, and fails on any of: the service not active; no `speakerd: playing:` since its last start; the live `speakerd` sink not the drop-in's (priority.session 1500, priority.driver 0), or speakerd's `*** NO INPUT SINK CONFIGURED` line; the default sink being device.json's amplifier (a stream with no target would play straight into it; it says to `wpctl set-default` the id of `speakerd input`, and only warns when the default is anything else that is not `speakerd`); an unreadable device.json; a limits line that is not exactly `speakerd: device: limits: output at <g> dB, tweeter <muted|on>` (any suffix, the fail-safe's included) or is missing, or limits that differ from device.json; a deploy reads exactly `... output at -20 dB, tweeter muted` (lifted limits, `{0, on}` after a smoke test, are a warning); a `device.json: FAILED` line; the links `speakerd:monitor_* -> speakerd-dsp:input_*` and `speakerd-dsp:output_woofer/tweeter -> <amp>:<port>` missing; anything else playing into the amplifier; an AudioPluginHost running; the speakerd sink driving (`pw-profiler`; "NOT measured" when nothing ran: either nothing played, or PipeWire has no `libpipewire-module-profiler`, see step 4 below); a restart (`NRestarts`, `MainPID`, the history), an xrun line (speakerd, PipeWire, WirePlumber journals) or `lost PipeWire`/`stopping` within `--window` seconds (10). It says which layer plays (passthrough is a warning), where snapclient plays, whether speakerd has a real-time thread, and the default sink.
- **Test hooks** for the virtual pair (`tests/vpair/test_firmware_speakerd_install.py`, `test_speakerd_crash_restart.py`, `test_speakerd_installed.py`; the installer tests use the stand-in speakerd of `tests/vpair/stub_speakerd.c`, which says the version they give it): `--home DIR` (install into DIR as the user's home, as the current user; the live checks are skipped only when no PipeWire is reachable, and `/etc` is not searched for autostarts), `--no-systemd` (print the systemctl calls), `--log FILE` (smoke reads speakerd's output from FILE); and three environment settings, `SPEAKERD_PLUGIN_HOST_NAME` (the process name instead of AudioPluginHost: a test never sees, waits for or stops this machine's own), `SPEAKERD_SYSTEM_LV2_DIRS` (instead of the system LV2 folders) and `SPEAKERD_START_WAIT` (the start check's 15 s). Those tests run the real installer, unit file, wrapper and drop-in; the systemd path runs against stand-ins for `systemctl` and `journalctl`, and the remote mode through a stand-in `ssh` that runs the board's side on the same machine, as `nobody`. No agent runs the remote mode against a board.

### Rates

The repository's `pipewire.conf` pins the graph to 44100 Hz (`default.clock.rate` and the amplifier's `audio.rate`), while snapcast streams 48000 (`snapcast-setup.sh --sampleformat 48000:32:2`). So PipeWire resamples the stream, and speakerd's plugins run at 44100: the crossover and firConv filters must be designed for the rate the board runs at. Nothing changes the rate silently: `speakerd-setup.sh` says what it found; `setup.sh --base-conf --rate 48000` installs the repository's `pipewire.conf` with both values changed (a drop-in cannot change the amplifier object's `audio.rate`, so `--rate` needs `--base-conf`).

### The tweeter rule (`speakerd/tweeter_rule.py`)

**Only a crossover's high band may reach the tweeter.** Walking from the input node (every
channel, Mine included) along every connection, a node's outputs carry the stream unfiltered for a
tweeter, except a crossover's output 1, its high band (output 0 is its low band, the woofer's; the
crossover's README). A crossover is a node whose plugin identifier's last segment starts with
`crossover`, not bypassed and not a `_control` build (an editor with no DSP). A document breaks the
rule when such an unfiltered output reaches the output node's channel 1 (the tweeter): the stream
straight, through any other plugin, through a bypassed crossover or a control build, or a
crossover's low band. What does not come from the input does not.

`speakerd/tweeter_rule.py` is the rule's one definition (standard library only). `setup-helper.py
graph` imports it: the installer checks every factory graph it installs or keeps, and `limits`
checks every layer before it turns the tweeter on. ampd imports it (installed beside it as
`bin/tweeter_rule.py`): while its speaker's `device.json` says `"tweeter": "on"`, it refuses every
revision that breaks the rule, a proposal on the hub (`rejected`, "<speaker>: the tweeter is on
here (device.json) and ..."), an adoption, and an apply on an agent (`failed`, which rejects the
proposal and rolls the other speaker back). speakerd applies the same rule (its README).

## ampd on a board (`ampd/`, `ampd-setup.sh`)

`ampd` is the speaker's **network agent**, and on the left speaker the **hub**: step 3 of `docs/remote-plugin-host.md`, speaking `docs/protocol.md` (version 1, with its "Clarifications"). It never touches audio: `speakerd` plays without it, and keeps playing when it stops, restarts or crashes. One Python file, `ampd/ampd.py` (Python 3.9 or later, the standard library only: a board has no pip; asyncio on one thread, the files written on a worker thread so a slow disk holds nothing up).

```
ampd --config ~/.local/state/speakerd/ampd.json --state-dir ~/.local/state/speakerd
     [--socket PATH] [--runtime-dir DIR] [--listen ADDR] [--hub-address ADDR]
     [--control-port 7450] [--knob-port 7451] [--monitor-port 7452] [--hub-control-port 7450]
     [--lkg-after SECONDS]
ampd --config FILE --check-config        # says what ampd.json says, exit 0, or why not, exit 2
ampd --version
```

| Option | |
|---|---|
| `--config` | `ampd.json` (below), required |
| `--state-dir` | speakerd's state directory: ampd reads `device.json` (the role it reports) and the layers, and writes `graph.json` and `graph.lkg.json` |
| `--socket` | speakerd's local socket; default `$XDG_RUNTIME_DIR/speakerd/control.sock`, speakerd's own default |
| `--runtime-dir` | where `status.json` goes; default `$XDG_RUNTIME_DIR/ampd` |
| `--listen`, `--hub-address` | instead of `ampd.json`'s |
| the ports | the protocol's 7450 (control, TCP), 7451 (knobs, OSC over UDP) and 7452 (monitor, TCP), on the listen address; `--hub-control-port` is where an agent finds the hub |
| `--lkg-after` | seconds a revision plays with no speakerd restart before `graph.json` is promoted to `graph.lkg.json`; default 60 (section 8 of the design). The virtual pair tests use 2 to 4 |
| `--check-config` | reads `ampd.json`, says what it says (never the secret, only whether there is one) and exits |

| Exit status | |
|---|---|
| 0 | stopped by SIGTERM, SIGINT or SIGHUP (after writing what was pending); `--check-config`, `--version` |
| 2 | a bad command line, an `ampd.json` it refuses, no state directory: the unit does not restart it |
| 3 | it cannot listen (the address is not this machine's, or a port is taken): the unit restarts it every second |

**`ampd.json`**, next to `device.json`, written by the installer (mode 600: it holds the secret), never by ampd or the hub: `{"version": 1, "name": "left", "hub": true, "listen": "0.0.0.0", "hub_address": null, "secret": "..."}` on the left speaker, `{"version": 1, "name": "right", "hub": false, "listen": "0.0.0.0", "hub_address": "bpi-amp.local", "secret": "..."}` on the right (the hub's real address comes from the person installing, never from a tracked file; mDNS replaces it later). ampd refuses a file with another key, a `version` other than 1, a name that is not letters, digits, `.`, `_` and `-` (at most 64), an agent with no `hub_address`, or a `secret` that is not 16 to 256 printable characters with no space. Without a secret it runs, says loudly that anyone on the network may control the speaker, and accepts every hello; the installer always writes one.

**The pair's secret.** The same secret is in both speakers' `ampd.json`; it never crosses the network and is never printed (`status` shows `(set)`). Whoever opens the control link (a controller, an agent) or a monitor link proves it: the speaker sends its `hello` first, with a `nonce` (a fresh random hex string), and the peer's `hello` carries `"auth"`: hex HMAC-SHA256, keyed with the secret, of `<nonce>:<role>:<name>` (its own `role` and `name`, as in that hello). A hello that does not prove it gets `{"op":"error","about":"hello",...}` and the connection closes. So a controller reads the hub's hello before it sends its own (the hub's hello already came first), and on the monitor link, which had no hello, the speaker now sends `{"op":"hello","role":"speaker","name":..,"nonce":..,"protocol":1}` and the controller answers `{"op":"hello","role":"controller","name":..,"auth":..}` before any `subscribe`. OSC is taken only from an address where an authenticated controller is connected (the hub) or from the hub this agent is connected to (an agent). An agent that proves the secret replaces a connected agent of its name (its ampd restarted); without a secret in `ampd.json` a second one is refused.

**Limits.** A document has at most 64 nodes and 512 connections; the hub takes 32 control connections (controllers and agents), each speaker 32 monitor clients of 32 subscriptions each; a peer that leaves more than 1 MiB unread (an agent or speakerd 256 MiB: documents are big) is dropped, so nothing queues for it; a whole number beyond ±10^15 is no value. A stream is exactly `output/level` or `node/<uid>/mon_<id>` with a uid of 16 or more (at most 10 digits) and an id of 1 to 64 letters, digits and `_`; speakerd's refusal of a subscription goes to its subscribers. One message that breaks something is said (`ignored a message from ...`) and ends nothing; a revision `time` that is not `YYYY-MM-DDThh:mm:ss[.f]Z` counts as none.

**What it does**, both roles: it connects to speakerd's socket, and again every second while it cannot (also while speakerd says `busy`), and passes parameters and revisions on to it. It serves the monitor link: each controller's subscriptions go to speakerd as their union, at the highest rate any asked (at most 60 Hz), and each controller gets the newest value of each stream at its own rate; nothing queues in ampd. It writes `graph.json` (the current revision's document with the current values folded into its nodes' `params`, with its `time` and `origin`; the hub adds its `seq`) atomically (a temporary file, fsync, rename, fsync of the folder), at once when a revision is applied and at most once a second while values change, and promotes it to `graph.lkg.json` once its revision has played `--lkg-after` seconds with no speakerd restart. It sends values to speakerd with seq 0 (always applied, in order): it orders them itself. When speakerd restarts under it, it gives it every value again (`graph.json` may lag by a second); a freshly started ampd gives none (speakerd's are the newest). When speakerd plays another revision than ampd's from a fallback layer (last known good, factory, passthrough), ampd follows it: it reads that layer's document. When it plays an older revision from the current layer (it ran on while ampd wrote a newer `graph.json` with the link down), it gets ampd's revision. An apply goes to speakerd as soon as it is decided, in order with the values around it: speakerd carries a value that arrives while a revision builds over into the new graph (protocol.md, clarification 18), so ampd keeps every value set while an apply is under way, and the new revision has it in its `graph.json`, in the graph sent to the controllers and in what a restarted speakerd is given (it says `revision <n>: keeps <k> value(s) changed while it was applied`).

**The hub** (`"hub": true`) stamps every change with its seq (persisted in `graph.json`: it goes on from it after a restart), applies it to its own speakerd, sends it to every agent and echoes it to every controller (OSC, and over the control link when it came over it; a value given as text over the control link only). It answers a change it cannot address (a node or a parameter the current revision does not list, any `mon_`) with an error; keeps who drags what, and ends a gesture with no end after 5 s (a value from the dragger restarts the 5 s); applies a proposed revision on every speaker that is up, all or nothing (10 s per speaker; a failure or a silence sends the previous revision back to those that applied it, and a speaker that applies it late gets the current one again); catches an agent that connects up (the current revision, then every value), or adopts its revision when it is newer (by time, then origin); and sends every controller the whole `state` when a speaker comes or goes or changes layer, and after an adoption. **An agent** applies what the hub sends, a newer seq only (the exact control-link copy of a value wins over its OSC copy, a 32-bit float, with the same seq), and tells the hub what its speakerd plays (`{"op":"status",...}`).

**`status.json`** (`$XDG_RUNTIME_DIR/ampd/status.json`, a tmpfs, rewritten whenever something changes, removed at a stop): its pid, name, role and revision, whether it is connected to speakerd (with speakerd's version, layer and revision) and, on an agent, to the hub; on the hub, the agents and the controllers. `ampd-setup.sh status` and `smoke` read it.

## The whole architecture (`setup.sh`)

`setup.sh` installs the audio side of a speaker by component, in the order the speaker boots them (docs/remote-plugin-host.md, section 8): **pipewire** (the speakerd sink drop-in via `speakerd-setup.sh sink`; with `--base-conf` the repository's `pipewire.conf`, with `--rate`; PipeWire restarted if anything changed), **snapcast** (`snapcast-setup.sh --mode target --server-ip … --route speakerd`, or only `--routing-only` for an installed snapclient), **speakerd** (`speakerd-setup.sh install`), **ampd** (`ampd-setup.sh install`: `ampd.json` and its unit; `--name`, `--hub`, `--agent`, `--hub-address`, `--listen`). `--only`/`--skip` choose components, `--route plugin-host` keeps the AudioPluginHost route. It checks every chosen component before it changes any (`speakerd-setup.sh check`, the bundle, the sink before `--route speakerd`, snapclient installed or `--server-ip`; `--route plugin-host` together with the speakerd component is refused, since it would leave the AudioPluginHost's rule on the amplifier), then stops the AudioPluginHost (`--stop-plugin-host`) before anything restarts PipeWire, then installs. That check is made whenever a chosen component restarts PipeWire into the speakerd route (pipewire, speakerd, snapcast with `--server-ip`), `--only pipewire` included: a running AudioPluginHost refuses it, or with `--stop-plugin-host` is stopped first. With `--route plugin-host` and no speakerd the plugin host is what plays, and stays. The pipewire component ends with the live check of the speakerd sink, and a PipeWire restart that fails stops everything before anything is routed into speakerd. It runs as the audio user (sudo is used inside snapcast-setup.sh where root is needed), takes `--dry-run` and the test hooks. `--mode target-remote` copies one bundle (artifacts only when speakerd is chosen) and runs `setup.sh --mode target` on the board, also for `--dry-run` (the board-side dry run); it builds nothing and lists the `tools/build.sh … aarch64` commands for what is missing.

## `tools/board.sh` (the `/board` skill's script)

`tools/board.sh status|journal|deploy|smoke|rollback` is the only way an agent reaches a board (rung 3 of `docs/autonomous-development.md`). The board is `$BOARD_USER@$BOARD_HOST` from the environment or `local.mk`. It refuses everything while `.claude/lab.lock` exists (this checkout's or the main one's), and `deploy`, `smoke` and `rollback` unless `tests/.status/<HEAD>.json` says `unit: pass` and `vpair: pass`, both run on a clean tree, and the tree is clean now (the pre-bash hook gates the same, and so do the installers' remote modes it calls; `BPI_DEPLOY_OVERRIDE=1`, a person's, bypasses the status, is logged, never the lock). It checks its arguments before the gate. `deploy` takes only `--role`, `--plugin`, `--factory`, `--import-filtergraph`, `--only` and `--skip`, and ampd's `--name`, `--hub`, `--agent`, `--hub-address` and `--listen` (anything else — `--base-conf`, `--rate`, `--stop-plugin-host`, `--server-ip`, `--no-restart`, ... — is a person's, who runs `firmware/setup.sh` directly), runs `tools/build.sh speakerd aarch64` and each plugin's aarch64 build, then `setup.sh --mode target-remote` (default `--only speakerd`). `journal [-n N] [--follow] [--unit speakerd|ampd]` is `journalctl --user -u speakerd -b` (or `-u ampd`) with `N` a whole number, quoted. `smoke` includes ampd's smoke when ampd is installed. `status` runs the board's **installed** `~/.local/lib/speakerd/current/setup/speakerd-setup.sh status` with a fixed command: nothing is copied to the board, so a read never runs an untested script there. `smoke` and `rollback` run the tested tree's speakerd-setup.sh remotely. Nothing in it lifts the cap. `--dry-run` prints what it would run.

### Open at the board (a person answers these before the cap is lifted)

- Which amplifier port drives the woofer and which the tweeter (the default is FL woofer, FR tweeter; the tweeter stays muted until then).
- The amplifier's node name on the running board (`bpi-alsa-playback-pcm` or `alsa-playback-pcm`), and whether its config gives it a `priority.driver` above 0.
- 44100 or 48000 Hz, and whether the factory graph's filters were designed for that rate.
- Where the AudioPluginHost's current `.filtergraph` session lives, for `--import-filtergraph`, and whether AudioPluginHost starts by itself at boot or login. **Save the session in AudioPluginHost first** (its File menu): the file on disk, not the window, is what is converted.
- Whether the bundle's crossover and firConv are the **same tuning, at the board's rate, as the session's**: the conversion keeps the session's parameters, but the plugin code is the bundle's, built from the deployed commit. Compare with the copies the session loads today (the board's `~/.lv2`: their versions and dates) and with the session's own settings and filter files; a different crossover build can put other frequencies on the tweeter.
- Whether `Ap.cap` exists in the board's PipeWire (the route uninstall restores), whether speakerd gets a real-time thread (RTKit, or `RLIMIT_RTPRIO` for the user: smoke says), and whether WirePlumber restores a remembered target for snapclient over client-rt.conf's (smoke says where snapclient plays).
- Whether the board's PipeWire loads `~/.config/pipewire/pipewire.conf.d` (it does not when started with another config name or with `PIPEWIRE_CONFIG_DIR`: install then refuses at the live check).
- Whether the audio user can read its journal (`journalctl --user -n 5` shows entries). Armbian may keep a volatile or unsplit journal, or the user may not be in the `systemd-journal` group; then nothing here can check what speakerd says, and install fails at its start check.

### First deploy, step by step (a person, at the board)

On the development machine, once: check out the commit to deploy (the merged branch) and **only then build**, so the artifacts are that commit's: `tools/build.sh speakerd aarch64`, `tools/build.sh loudness aarch64 headless`, and `tools/build.sh crossover aarch64 complete` and `tools/build.sh firConv aarch64 complete` if the session uses them (then add `--plugin crossover:complete --plugin firConv:complete` below). speakerd says the commit it was built from; install warns when it is not the bundle's, and `status` shows both. That commit is green on a clean tree (`tools/test.sh all`: the remote modes refuse otherwise), and `firmware/local.mk` names `BOARD_HOST` and `BOARD_USER` (the audio user). The scripts called below on the board are the installed copies, made executable by the install.

1. **Look first, change nothing.** On the board, as the audio user, with nothing streaming (pause the snapserver source): `journalctl --user -n 5` must show entries; `loginctl show-user "$USER" -p Linger` must say `Linger=yes` (else the speaker plays only while someone is logged in); note what `wpctl status` says (the default sink, whether `Ap.cap` exists under Sinks and `Ap.play` under Sources, where snapclient plays) and where the AudioPluginHost's `.filtergraph` session lives. Save that session in AudioPluginHost (its File menu), and answer "Open at the board" above, the crossover's tuning included.
2. **speakerd alone; snapclient stays on `Ap.cap`.** From the development machine, the board-side dry run, then the same without `--dry-run`:
   `firmware/setup.sh --mode target-remote --only speakerd --role left --stop-plugin-host --plugin loudness:headless --import-filtergraph /home/user/<session>.filtergraph --dry-run`
   (`--role right` on the right speaker.) Read what it found (the amplifier and its ports, the rate, the plugin host and what starts it, the factory graph). It refuses while anything but a systemd unit would start the AudioPluginHost again at boot or login, naming each and what to remove; remove them and run it again. If it refuses because the tweeter would get something other than a crossover's high band, the session sends its high band to the port `device.json` calls the woofer: the session and the port convention disagree, so find out which is right (`--woofer-port`/`--tweeter-port`) before going on. The real run stops the AudioPluginHost, disables its units, installs the drop-in, restarts PipeWire, checks the live sink, installs speakerd capped, starts it and checks its limits line. The speaker is silent from here to step 4: nothing plays into the speakerd sink yet.
3. **Confirm the sink is the drop-in's.** On the board: `~/.local/lib/speakerd/current/setup/speakerd-setup.sh status` must say `live sink: the drop-in's (priority.session 1500, priority.driver 0); default sink speakerd`. If the default sink is anything else (a person chose one with `wpctl` before), make it speakerd: `wpctl status`, find the id of `speakerd input` under Sinks, `wpctl set-default <that id>`, and `status` again. Then `systemctl --user restart speakerd` and `journalctl --user -u speakerd -b` (everything since boot, not only the last lines): after the last `speakerd-run: starting speakerd`, `input sink 'speakerd' exists: using it`, the exact `device: limits: output at -20 dB, tweeter muted`, and no `NO INPUT SINK CONFIGURED`.
4. **Route snapclient into speakerd, then smoke.** `firmware/setup.sh --mode target-remote --only snapcast` (it refuses unless the live sink is the drop-in's, and unless the snapclient unit reads client-rt.conf). **The first sound is a check by ear:** stand at the speaker and start the stream at its lowest level; only the woofer may sound (the tweeter is muted). If anything comes from the tweeter, pause the stream at once, `systemctl --user stop speakerd` on the board, and stop the procedure: the wiring contradicts both the convention and the session. Then, with the quiet stream playing, `tools/board.sh smoke` (or on the board `~/.local/lib/speakerd/current/setup/speakerd-setup.sh smoke`): every check must pass, "amplifier drives the graph" included, and when a session was imported its `layer:` line must name `factory (factory.json)`, not passthrough (passthrough means the import or a plugin bundle is missing: a forgotten `--plugin crossover:complete`, for example). If it says who drives was **NOT measured** although smoke also says snapclient plays into the speakerd sink, this PipeWire has no profiler module (the repository's `pipewire.conf` loads it; a board's own may not): add `~/.config/pipewire/pipewire.conf.d/50-profiler.conf` containing `context.modules = [ { name = libpipewire-module-profiler } ]`, run `systemctl --user restart pipewire wireplumber`, then `systemctl --user restart snapclient` (speakerd restarts by itself), and smoke again with the stream playing.
5. **Reboot, then status and smoke again.** Check `Linger=yes` once more (step 1), `sudo reboot`, and once the board is up, **before logging in to it**, wait a minute; then log in and check that speakerd started at boot, not with your login: `systemctl --user show speakerd -p ActiveEnterTimestamp` must be earlier than your login (`who -u`). With the quiet stream playing, step 3's `status` and step 4's smoke must pass again: the sink, the routing and speakerd come back by themselves, in that order, with no AudioPluginHost. If smoke finds an AudioPluginHost running, something the install's scan does not look at starts it (for example `/etc/xdg/lxsession/*/autostart`, openbox's `autostart`, `/etc/cron.d`, `/etc/profile.d`): find and remove it, reboot, and run this step again.
6. **By ear, with the cap.** At -20 dB the woofer alone plays: confirm which amplifier port is the woofer. If they are swapped, re-run step 2's command **without `--dry-run`** and with `--woofer-port playback_FR --tweeter-port playback_FL` (only those change), then smoke again. **If that re-run is refused** because the tweeter would get something other than a crossover's high band, the session and the ears disagree about the wiring: stop there, with the cap on, and find out which is wrong before anything else.
7. **Lift the cap in two stages,** a person at the speaker, in their own shell; no agent and no script does this. First the tweeter on, the output still at -20 dB: `~/.local/lib/speakerd/current/setup/speakerd-setup.sh limits --gain-db -20 --tweeter-limit on --person-present` (it refuses if any layer speakerd may load feeds the tweeter other than through a crossover's high band). Check with a quiet 80-100 Hz tone and an ear close to the tweeter that it carries no bass (a hand test is unreliable on a dome tweeter; a near-field measurement with `dsp/python_dsp_tools` is better still). If it does, mute at once with `systemctl --user stop speakerd` (snapclient keeps playing into the speakerd sink and nothing reaches the amplifier), then `~/.local/lib/speakerd/current/setup/speakerd-setup.sh limits --cap`, which starts speakerd again, capped. Then raise the output in steps, listening at each: `--gain-db -14`, `-8`, `-3`, and `0` (no limit), each with `--tweeter-limit on --person-present`.

Back out at any point with `uninstall` (when snapclient is routed into speakerd, its routing from before speakerd goes back, or snapclient is stopped and disabled if that routing's target is not in the running PipeWire; the AudioPluginHost units install disabled are re-enabled, but not the autostarts a person removed in step 2; speakerd and its sink are removed): `~/.local/lib/speakerd/current/setup/speakerd-setup.sh uninstall`. If a first install stopped before any version was installed (so that script does not exist on the board yet), run `firmware/speakerd-setup.sh uninstall --mode target-remote` from the development machine: it works with no version present and re-enables the units recorded as disabled. On a **first deploy there is nothing to roll back to**, so only `uninstall` applies; after a later deploy, `rollback` makes the previous version current again, capped (-20 dB, tweeter muted) until step 7 is done again.

## USB-C serial console (`usb-serial-console-setup.sh`)

`usb-serial-console-setup.sh` turns the CM4's USB-C OTG port into a **post-boot serial console over USB** using the in-kernel CDC-ACM gadget (`g_serial`). The board appears to a connected PC as `/dev/ttyACM0` and locally as `/dev/ttyGS0` with a login prompt. It writes `/etc/modprobe.d` + `/etc/modules-load.d` entries (so `g_serial use_acm=1` loads at boot), an optional ModemManager-ignore udev rule, enables `serial-getty@ttyGS0`, and (with `--kernel-console`) appends `console=ttyGS0,115200` to `/boot/armbianEnv.txt` extraargs and adds `g_serial` to the initramfs.

- `--mode local` (default) configures the machine it runs on (the CM4); `--mode remote --target-host [user@]host` `scp`+`ssh`'s it to the board and runs it with `sudo`.
- Relies on what the repo's kernel/DT already provide: USB-C `dr_mode = "peripheral"` (`...cm4io.dts`), `CONFIG_USB_DWC2=y` (the g12b OTG peripheral controller), `CONFIG_USB_G_SERIAL=m`, `CONFIG_U_SERIAL_CONSOLE=y`. Preflight checks `modinfo g_serial` and `/sys/class/udc`.
- **Limitation:** this is a post-boot console only — it cannot show bootrom/U-Boot/early-kernel output (the port is USB, not a UART). For low-level boot debugging use the AO UART (`&uart_AO`, already the console). `--dry-run` previews all changes.

## WiFi driver selection (`wifi-driver-setup.sh`)

The on-module WiFi is a **Realtek RTL8822CS** (SDIO 802.11ac + BT combo, on `&sd_emmc_a` at 200 MHz SDR104 1v8 — DT already tuned in `meson-g12b-bananapi-cm4.dtsi`, `amlogic,dram-access-quirk` deleted). It can be driven by **either** the mainline in-tree `rtw88` stack (`rtw88_8822cs`+`rtw88_sdio`+`rtw88_8822c`+`rtw88_core`) **or** Realtek's out-of-tree vendor **`88x2cs`** module. Both are present on the board and, if both load, they race for the SDIO function — a source of instability *and* slowness. **The vendor `88x2cs` is the fast path** (measured 50 → ~150 Mbit/s just by switching away from rtw88; rtw88 tops out ~270 Mbit/s here, 88x2cs reaches ~400+). Mainline `rtw88` also ignores runtime `iw … power_save off` (its firmware LPS throttles throughput regardless).

`wifi-driver-setup.sh` pins **one** driver by blacklisting the other and rebuilding the initramfs, and disables WiFi power-save. Default `--driver 88x2cs`; pass `--driver rtw88` to standardize on mainline.
- Blacklist file: `/etc/modprobe.d/blacklist-rtw88-8822cs.conf` (for 88x2cs) or `/etc/modprobe.d/blacklist-88x2cs.conf` (for rtw88); re-running with the other `--driver` flips them cleanly. Each file carries **both** `blacklist <mod>` **and** `install <mod> /bin/true` for the bad driver — the `install … /bin/true` is the hard block that prevents loading via alias, as a dependency, *or* via explicit `modprobe`. This is necessary because both drivers claim the **same SDIO alias**, so a soft `blacklist` alone can race (both have been observed loaded at once). Then `update-initramfs -u` so the blacklisted module isn't pulled in early and grab the radio first.
- Power-save off: prefers a NetworkManager drop-in `/etc/NetworkManager/conf.d/wifi-powersave-off.conf` (`wifi.powersave = 2`); falls back to a `wifi-powersave-off.service` systemd oneshot (`iw … set power_save off` over every wireless iface at boot) when NM isn't managing WiFi. `--keep-powersave` skips this. `--no-apply-now` skips the live `iw` toggle.
- The driver swap **only takes effect on reboot** (`--reboot` to do it, else the script prints the manual steps). Verify with `basename "$(readlink /sys/class/net/wlan0/device/driver)"` (→ `88x2cs` or `rtw88_sdio`) and measure real throughput over the LAN with `iperf3` (not an internet speed test).
- `--mode local` (default) configures the machine it runs on; `--mode remote --target-host [user@]host` `scp`+`ssh`'s it to the board and runs with `sudo`. `--dry-run` previews all changes. Preflight checks the RTL8822CS SDIO id (`024c:c822`) and that the chosen driver's module is installed (if `88x2cs` is missing it points at the `8822cs` dkms package).

## Kernel config

`defconfig` is the full board kernel config (base: `config-6.12.13-current-meson64`, an Armbian current-meson64 config). `make config` installs it into the kernel tree. When adding driver support (e.g. `CONFIG_SND_SOC_MAX98396`), edit `defconfig` here so the change is tracked.
